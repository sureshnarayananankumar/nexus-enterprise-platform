# 03 — API Communication Design

## 1. Communication styles

| Style | Used for | Technology |
| --- | --- | --- |
| REST (JSON over HTTPS) | Commands and queries from portals; service-to-service reads | Spring MVC, NestJS |
| GraphQL | Aggregated read views for dashboards (BFF) — avoids N calls from the browser | NestJS + Apollo in api-gateway |
| WebSockets | Live notifications, presence, collaborative updates, AI token streaming | realtime-service (Socket.IO), SSE for AI streaming |
| Kafka events | Asynchronous integration between services | Spring Kafka, KafkaJS, aiokafka |

## 2. REST conventions

- Base path: `/api/v{major}/{resource}` — e.g. `/api/v1/orders/{orderId}/lines`.
- Plural nouns, kebab-case paths, camelCase JSON.
- `POST` create (201 + `Location`), `GET` read, `PUT` full replace, `PATCH` partial (JSON Merge Patch), `DELETE` soft delete (204).
- **Idempotency**: state-creating `POST`s accept `Idempotency-Key`; the service stores the key + response hash for 24 h.
- **Concurrency**: responses carry `ETag: "<version>"`; updates require `If-Match` → `412` on mismatch.
- **Pagination**: `?page=0&size=20&sort=createdAt,desc`; max `size` = 100.
- **Filtering**: explicit query params (`status=OPEN&assigneeId=…`), never free-form SQL.
- **Headers**: `Authorization: Bearer <jwt>`, `X-Correlation-Id` (generated by gateway if absent), `Accept-Language`.

### Error contract (RFC 9457)

```json
{
  "type": "https://nexus.dev/problems/validation-error",
  "title": "Validation failed",
  "status": 400,
  "detail": "Request body has 2 invalid fields",
  "instance": "/api/v1/auth/register",
  "code": "VALIDATION_ERROR",
  "traceId": "8f0c2b1d9a4e4c1f",
  "errors": [
    { "field": "email", "message": "must be a well-formed email address" },
    { "field": "password", "message": "size must be between 12 and 128" }
  ]
}
```

Standard codes: `VALIDATION_ERROR` 400, `UNAUTHENTICATED` 401, `FORBIDDEN` 403, `NOT_FOUND` 404, `CONFLICT` 409, `PRECONDITION_FAILED` 412, `RATE_LIMITED` 429, `INTERNAL_ERROR` 500.

## 4. Kafka event design

### Topics

One topic per aggregate family, keyed by aggregate ID (preserves per-aggregate ordering):

| Topic | Partitions (prod) | Retention |
| --- | --- | --- |
| `nexus.identity.events` | 6 | 7 days |
| `nexus.organization.events` | 6 | 7 days |
| `nexus.employee.events` | 6 | 7 days |
| `nexus.customer.events` | 12 | 7 days |
| `nexus.project.events` / `nexus.task.events` | 12 | 7 days |
| `nexus.order.events` / `nexus.inventory.events` / `nexus.finance.events` | 12 | 14 days |
| `nexus.document.events` | 6 | 7 days |
| `nexus.notification.commands` | 6 | 3 days |
| `nexus.audit.events` | 12 | 30 days (compliance copy also in MongoDB) |
| `*.DLT` | same as source | 30 days |

### Reliability patterns

```mermaid
sequenceDiagram
    participant API as order-service API
    participant DB as order_db
    participant RELAY as Outbox relay
    participant K as Kafka
    participant INV as inventory-service
    API->>DB: BEGIN; insert order; insert outbox(OrderPlaced); COMMIT
    RELAY->>DB: poll unpublished outbox rows (SKIP LOCKED)
    RELAY->>K: produce (key = orderId, acks=all, idempotent)
    RELAY->>DB: mark published
    K->>INV: OrderPlaced
    INV->>INV: if eventId in processed_events → skip
    INV->>INV: reserve stock + insert processed_events (one TX)
    INV-->>K: StockReserved (via its own outbox)
```

- Producers: `enable.idempotence=true`, `acks=all`.
- Consumers: manual commit after DB transaction; 3 retries with back-off → `*.DLT`.
- Sagas (order → payment → stock) are **choreographed**; compensations are explicit events (`OrderCancelled`, `StockReleased`).

## 5. WebSocket protocol (realtime-service)

- Connect: `wss://…/ws` with `auth: { token }` in the Socket.IO handshake; the token is verified against JWKS.
- Rooms: `tenant:{tid}`, `user:{sub}`, `project:{projectId}` (join only if the user is authorised — checked via project-service).
- Server → client events: `notification.created`, `task.updated`, `presence.changed`, `ai.token`.
- Client → server events are validated with JSON Schema and rate-limited per socket.

## 6. GraphQL BFF

Used only for **read aggregation** (dashboard widgets). Mutations stay REST to keep authorisation and idempotency in one place.
Query depth limit 6, complexity limit 500, persisted queries in production.

## 7. API documentation

Each Java service exposes OpenAPI 3 at `/v3/api-docs` and Swagger UI at `/swagger-ui.html`.
The gateway will publish an aggregated catalogue; exported specs are committed under `docs/api/` per release.
